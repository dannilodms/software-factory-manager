# 01: Turning staging on and off

**What to build:** From the maintainer's machine, one command turns staging on: a server comes up at Hetzner, prepared by the cloud-init file, and the command returns once the server answers SSH with the host key the tool gave it and cloud-init has finished. Another command turns it off and destroys it, and a third tells whether it is on, since when and at which address and host names. The tool is a Go command of its own, among the repository's tools, reaching the provider through an interface whose only adapter today is Hetzner's. See the spec, sections The tool and The server.

**Blocked by:** None (can start immediately).

**Status:** resolved

- [x] A Go command of its own, in the Go module of the API among the repository's tools and built into no image, has the commands to turn on, turn off and give the status of an environment. Task runs them as `staging:on`, `staging:off` and `staging:status`.
- [x] The choices of staging (provider, region, size, system image, server name) are in a committed file the tool reads: Hetzner, `fsn1`, `cx23` and the newest Ubuntu LTS that Docker supports officially.
- [x] The provider is an interface (create from a specification, find by name, destroy by name), with an in-memory implementation for the tests and a Hetzner adapter on `hcloud-go`.
- [x] The Hetzner adapter registers the deploy public key at the project, so Hetzner e-mails no root password, and removes it with the server. It asks for an ordinary IPv4 address that is deleted with the server, labels what it creates with the environment, and creates no firewall at Hetzner.
- [x] The Hetzner adapter is tested against a stand-in of Hetzner's API that answers as its documentation says. No test calls Hetzner.
- [x] One cloud-init file prepares the server:
  - Docker from Docker's repository, at the version the file names;
  - the deploy user in Docker's group, with the deploy public key;
  - the host key the tool generated;
  - SSH by key only, with no password and no root;
  - a firewall inside the server that lets in 22, 80 and 443 only;
  - automatic security updates;
  - a signal that it has finished.
- [x] Readiness is an interface: wait until SSH answers with the expected host key and cloud-init reports it has finished, within about ten minutes. Its SSH implementation is tested against an SSH server the test starts in-process, which also proves that a different host key is refused.
- [x] Turning on creates one server. Turning on when it is on creates nothing and reports. A failure after the server was created destroys it, removes the local key and exits with an error. Each is proven with the fake provider.
- [x] A copy of the deploy private key is kept in a git-ignored folder of the main checkout while staging is on, and removed when it is turned off.
- [x] The token is `HETZNER_TOKEN`, from `.env`. When the tool runs in a worktree it reads the `.env` of the main checkout. The name is not in `.env.example`.
- [x] No command prints a secret: the tests check what they print.
- [x] Turning staging on for real works, `ssh deploy@<address>` with the local key runs `docker version`, root and password logins are refused, and turning it off leaves nothing at the provider.
- [x] `docs/providers.md` describes the Hetzner project as it now is, and `CODING_STANDARDS.md` (Servers, Versions) and the `README.md` say how staging is turned on and off.

## Comments

### What was built

- `apps/api/tools/environment`, a `main` package of the API module: `environment on|off|status <environment>`, run by `task staging:on`, `task staging:off` and `task staging:status` (`dir: apps/api`, `go run`). One file per command (`on.go`, `off.go`, `status.go`); `run(ctx, arguments, variables, outside, stdout, stderr) int` returns 0, 1 or 2, and `outside` carries the working directory, the provider, readiness and the clock, so the tests give fakes.
- `deploy/server.staging.yaml`: `hetzner`, `fsn1`, `cx23`, `ubuntu-26.04`, server `staging`. The tool reads `deploy/server.<environment>.yaml` strictly (an unknown key, a missing one or a provider with no adapter stops it); a name with no file is not understood (status 2).
- `deploy/cloud-init.yaml`, a template of Go's `text/template` that stays valid YAML: the host key (`ssh_keys`, `ssh_deletekeys`, `ssh_genkeytypes: [ed25519]`, the other types deleted after the packages and `HostKey` so that sshd offers only this one), the `deploy` user with the deploy key, `ssh_pwauth: false`, `disable_root`, an sshd drop-in (`PermitRootLogin no`, `PasswordAuthentication no`, `AllowUsers deploy`), unattended-upgrades on, no recommended packages, Docker's apt source with its key inline, `docker-ce`, `docker-ce-cli`, `containerd.io` and `docker-compose-plugin` pinned, and a `runcmd` script that starts with `set -eu`: the deploy user into the `docker` group, ufw (22/tcp, 80/tcp, 443/tcp, 443/udp), `sshd -t`, `docker version`, and last the signal `/var/lib/software-factory-manager/server-prepared`.
- `provider` (the interface, `Specification`, `Server`, `ErrNameTaken`), `provider/providertest` (in memory, with knobs to fail a creation, to create and still fail, and to fail a destruction), `provider/hetzner` (hcloud-go v2.53.0).
- `sshclient`: `Dial` trusts only the given host key and offers the deploy key only after it; `Run` gives the exit status of a command; `Readiness` retries until the context ends, then runs `cloud-init status --wait` and checks the signal. `sshclient/sshclienttest`: an SSH server in the test's process, which records each command and its input in order, for ticket 05's remote server too.
- The local copy, `.servers/<environment>/` in the main checkout (`/.servers/` in `.gitignore`): `deploy-key`, `known_hosts` and `ssh_config`, so that `ssh -F .servers/staging/ssh_config staging` logs in. Folder and files are reached by their owner alone: mode 0700/0600 elsewhere, and on Windows a protected access list with the current user only (`owner_windows.go`, `golang.org/x/sys/windows`).
- Records: Servers, Configuration, Commands, Layout, Enforcement (control flow judges `tools/`) and Versions in `CODING_STANDARDS.md`; the Hetzner section and its summary row in `docs/providers.md`; Configuration and Deploy in `README.md` and `README.pt-BR.md`; a comment for ticket 04 in its file.

### Decided while building

- **The name.** The tool is `environment` (`go run ./tools/environment on staging`), since every command takes the environment's name; the verbs are on, off and status, never deploy or provision. The publish of ticket 05 is a fourth entry of `commands` in `main.go`: the provider is connected only by a command that asks for it (`environment.provider()`), so the publish needs no token.
- **The choices file** is `deploy/server.<environment>.yaml`, named like `compose.<environment>.yaml` but not a Compose file name, so the versions guard does not judge it as one.
- **The system image** is `ubuntu-26.04`: Docker's install page (https://docs.docker.com/engine/install/ubuntu/, read on 2026-11-19) lists Ubuntu Resolute 26.04 (LTS) as the newest LTS; Hetzner's changelog (https://docs.hetzner.cloud/changelog) offers `ubuntu-26.04` since 2026-05-18; Docker's repository has packages for `resolute`. Both sources and the date are in a comment of the file.
- **Docker's versions** are the newest in https://download.docker.com/linux/ubuntu/dists/resolute/stable/ on 2026-11-19: `5:29.10.0-1~ubuntu.26.04~resolute` for the engine and its command line, `2.4.2-4~ubuntu.26.04~resolute` for containerd, `5.8.0-1~ubuntu.26.04~resolute` for Compose. Buildx is not installed: the server builds nothing. Recommended packages are off, so that no package of Docker comes at a version the file does not name. Docker's signing key is inline, with its fingerprint, rather than fetched from a key server at boot.
- **Where those versions are checked.** The versions guard does not read either file; the tests of the tool check that each Docker package names an exact version built for the release of Ubuntu that the system image of every environment names, so the two change together (Enforcement in Versions).
- **cloud-init's own schema validator is not used**: no image of cloud-init is published pinned by version, and building one means installing cloud-init from Ubuntu's archive, which does not keep old versions, or from its source with its Python dependencies. That does not cost little. The tests check that the committed file is YAML, that the rendered file carries the keys where cloud-init reads them and fits Hetzner's 32 KiB, and the order of the steps; readiness fails at once on a failed cloud-init; the first real turn-on proves the rest.
- **The signal that cloud-init has finished** is a file the last step writes, after a script that stops at its first failure. Readiness accepts `cloud-init status --wait` exiting 0, or 2 (finished with a recoverable warning, which a key of the provider's own configuration can cause), when the file exists; status 1, or no file, ends the wait at once with an error.
- **After the first real turn-on** (by the orchestrator, 2026-11-19): cloud-init finished "degraded", because its schema refuses `ssh_genkeytypes: []` (at least one type), and the server had RSA and ECDSA host keys besides the given one, made again by the upgrade of `openssh-server` at the first boot (`/var/log/dpkg.log`, keys dated after it). Neither showed in the tests, nor stopped the turn-on, since readiness accepts status 2. Fixed in `deploy/cloud-init.yaml`: `ssh_genkeytypes: [ed25519]` keeps the given key (cloud-init makes only a type whose key is missing), runcmd deletes the RSA and ECDSA keys, the sshd drop-in sets `HostKey` to the ed25519 key alone, and runcmd's first step is `cloud-init schema --config-file /var/lib/cloud/instance/cloud-config.txt`. A file that breaks the schema then stops the script before the signal, and the tool destroys the server. That is cloud-init's own validator, run where it is installed at no cost; the provider's vendor-data is left out, so that a deprecation there fails nothing. The fixed file is valid for cloud-init 26.2 (`cloud-init schema --config-file`, in `ubuntu:26.04`), and is proven on a server by the real turn-on of ticket 02.
- **Port 443** is let in for TCP and UDP (HTTP/3). Docker publishes ports past ufw: that rule is in Ports, in Servers, and in a comment of ticket 04.
- **Host names** write the address with dashes, one label under `sslip.io` (`app.203-0-113-10.sslip.io`).
- **A turn-on cut short** by a signal still destroys what it created: the undo runs on a context that the shutdown notice does not end, for up to five minutes.
- **A name already taken** at the provider (another turn-on may be creating the server at that moment) fails without destroying anything, and says to turn staging off and on again once none runs.
- **On, but no local copy** (staging turned on from another machine): turning on fails, destroys nothing and says to turn it off and on; the status says this machine keeps no key.
- **Off with no server** still asks the provider to destroy by name, which removes a deploy key a cut turn-on left behind.
- **The address goes with the server**: the reference of Hetzner's API does not say that an IPv4 created with a server is deleted with it, so the adapter deletes it after the server when Hetzner kept it.
- **Labels**: `environment=<name>` on the server and the key; Find and Destroy select by name and by that label.
- **Status** dates the server by its creation at the provider and tells its age; ticket 02 adds the pull request.
- **Dependencies**: `github.com/hetznercloud/hcloud-go/v2 v2.53.0` is new (it brings `prometheus/client_golang` and its own into `go.sum` as indirect requirements, compiled into the tool alone); `golang.org/x/crypto v0.58.0` and `golang.org/x/sys v0.50.0` move from indirect to direct, at the versions they had.
- **After the code review** (2026-11-20): the token, the password of Mailpit and both private keys stay `config.Secret` until the file, the template (`.HostPrivateKey.Reveal` in `deploy/cloud-init.yaml`) or `gh` that uses each; the deploy key, its text and the host key travel as one `loginKeys`, which gives the SSH target at an address; the unit `containers-without-metadata.service` of the cloud-init file drops, in `DOCKER-USER`, what a container sends to Hetzner's metadata service, which serves the private host key, on every boot after ufw and before Docker (valid for cloud-init 26.2 and `systemd-analyze verify`, in `ubuntu:26.04`; a real server proves it); and "no test calls Hetzner or GitHub" is in Tests of `CODING_STANDARDS.md`.
