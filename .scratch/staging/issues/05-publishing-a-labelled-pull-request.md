# 05: Publishing a labelled pull request

**What to build:** A pull request from this repository with the `staging` label is published to staging once its checks pass. The pipeline pushes the images of the commit to the GitHub container registry and runs the tool's publish command. That command logs in over SSH and writes the variables file, after checking that every name of `.env.example` has a staging value. It then starts the data again, applies the migrations, runs the seed and starts the API and the worker. A comment on the pull request gives the address of the app and of Mailpit. When staging is off, the job skips with a notice and passes. See the spec, sections The publish and The pipeline.

**Blocked by:** 02, 04.

**Status:** resolved

- [x] The tool has a publish command. Its inputs are the commit, the pull request, the address, the host key, the deploy key and the password of Mailpit.
- [x] The remote server is an interface (write a file, run a command), with an in-memory implementation that records both in order, and an SSH implementation that trusts only the given host key.
- [x] Every name of `.env.example` has a staging value of one of four kinds: fixed, derived from the address, drawn at random on each publish, or deliberately empty. A name with no decision stops the publish before any remote step. A test adds a name and proves it.
- [x] The steps run in the order the spec gives:
  1. copy the files;
  2. write the variables file, readable by the deploy user alone;
  3. pull the images;
  4. stop the API and the worker;
  5. remove the volumes of PostgreSQL and Garage;
  6. start PostgreSQL, Garage and its rule, Mailpit and Caddy;
  7. run the migration, then the seed;
  8. start the API and the worker;
  9. wait for `/up`.

  A test with the fake server proves this order.
- [x] Neither the command nor the job prints a value, the variables file or the configuration of a container. A test checks what the command prints.
- [x] A job of `ci.yml` runs after `Checks`, only for a pull request from this repository with the label, in the GitHub Environment `staging`. It pushes the three images tagged with the commit and runs the publish. The required check does not change.
- [x] When the address variable of `staging` is empty, the job skips with a notice and passes.
- [x] Publishes share one concurrency group, and a running one is never cancelled.
- [x] The job asks for writing packages and pull requests and only reading the contents. actionlint and zizmor pass.
- [x] The published pull request gets a comment with the address of the app and of Mailpit.
- [x] For real: the pull request of this effort, labelled, is published to a staging that is on. The app opens on the login screen over HTTPS, a login code asked for a user of the seed arrives in Mailpit, and logging in with it reaches the shell.
- [x] `CODING_STANDARDS.md` (Publishing, Secrets, Seed) matches what was built.

## Comments

### What was built

- **The publish command**, `environment publish staging` (`apps/api/tools/environment/publish.go`), a fourth entry of `commands`. Its six inputs come from the variables of the process, under the names the GitHub Environment holds them by: `COMMIT`, `PULL_REQUEST`, `SERVER_ADDRESS`, `SERVER_HOST_KEY`, `DEPLOY_KEY` and `MAILPIT_PASSWORD`. Each is checked before it logs in (a full hash, a number, an IPv4 address, a line of known hosts that names that address, a private key OpenSSH reads); a missing or unreadable one is named, never printed. It needs no token of the provider. It prints each step, numbered as the spec numbers them, then the host names.
- **The staging values** (`variables.go`): `stagingValues` decides every name of `.env.example` with one of four constructors, `fixed`, `derived`, `random` and `deliberatelyEmpty`. The variables file is `staging/.env` on the server, mode 0600: every name of `.env.example` in its order, empty or in single quotes, under a comment naming the commit and the pull request.
- **The remote server**: the interface `remoteServer` (`WriteFile` with a mode, `Run`, `Close`); the in-memory one in `main_test.go`, `fakeServer`, which records every file and command in one journal with the wait for `/up` and fails the commands a test names; and `sshclient.Open` and `Remote`, which log in through `Dial` (only the given host key), write a file as `umask 077 && mkdir -p … && cat > ….new && chmod … && mv -f …` with the content on standard input, run a command and fail on a status other than 0, and send what the commands print to the output of the publish. `sshclienttest.Server` gained `Print`.
- **The wait for `/up`** (`up.go`): `upOverHTTPS` asks `https://app.<address>.sslip.io/up` from where the tool runs, every 5 s, until a 200, trusting the system's certificate authorities, for up to 5 minutes; giving up, it says what the last answer was.
- **The comment**: `CommentOnPullRequest` on the GitHub interface; `gh pr comment <n> --body-file -` with the body on standard input in the `gh` adapter; kept in memory by `githubtest`. The comment gives the app, Mailpit with its user `maintainer` and the name `STAGING_MAILPIT_PASSWORD`, and `seed+admin@fabrica.example`.
- **The job** `staging`, "Publish to staging", of `ci.yml`: after `Checks` and not in its `needs`, only for a pull request of this repository with the label, in the GitHub Environment `staging`, in the concurrency group `staging` with no cancel, with `contents: read`, `packages: write` and `pull-requests: write`, no cache, and 30 minutes. Its first step writes the notice and skips the rest when `SERVER_ADDRESS` is empty. Then it checks out the commit, installs Go, Vite+ with the dependencies of the app (not Chromium) and Task, builds the images with `task api:image`, `task caddy:image` and `task seed:image`, pushes them tagged with `GITHUB_SHA` under the names `deploy/compose.staging.yaml` runs, with a login to GHCR that lasts one step, and runs `go run ./tools/environment publish staging` with every value in `env:`.
- **The workflow's concurrency** (surprise 4): a new run of a pull request with the `staging` label no longer cancels the one before it.
- **The images** carry `LABEL org.opencontainers.image.source` (the API, the seed and the stage `servers` of Caddy), which links each package to the repository; the stage `development` of Caddy is unchanged.
- **Stale text** (surprise 9): the seed's output no longer says the administrator is the one the local login provider knows; the header of `.env.example` says where a new name gets its staging value.
- **Records**: Commands, Seed, Secrets (On the server, Checked first) and Publishing (Images, Staging, The publish of staging, Never cancelled) in `CODING_STANDARDS.md`; the Configuration table and Deploy in `README.md` and `README.pt-BR.md`; the container registry, the environment `staging` and the summary row in `docs/providers.md`.

### Decided while building

- **The second kind is "derived from what the publish is given".** Ticket 04 put `COMMIT` and `MAILPIT_PASSWORD_HASH` in `.env.example`, which the spec's "derived from the address" does not cover. The kind covers the address (the three origins), the commit, and the password of Mailpit (its bcrypt hash, cost 10, salted anew on each publish). In Checked first, in Secrets.
- **What the Compose file writes itself is deliberately empty** in the variables file (`DATABASE_URL`, `MIGRATION_DATABASE_URL`, `API_LISTEN_ADDRESS`, `FILE_STORAGE_URL`, `EMAIL_SENDER`, `EMAIL_SMTP_ADDRESS`), as are the ports of development, the telemetry, the local login provider, Resend, the tests and `ACME_EMAIL` (still open, below). The header of the file says so. A test proves that every `${NAME:?}` of the two Compose files of staging gets a value.
- **The random values**: 32 bytes in hexadecimal for the three passwords of PostgreSQL, `GARAGE_RPC_SECRET`, `FILE_STORAGE_SECRET_ACCESS_KEY` and `LOGIN_CODE_KEY`; `GK` and 12 bytes in hexadecimal for `FILE_STORAGE_ACCESS_KEY_ID`, Garage's form. Hexadecimal fits a URL, `psql`'s `\getenv` and Garage.
- **The fixed values** are the defaults of the binary and of `.env.example`; `SEED_MAILBOX` keeps `seed@fabrica.example`.
- **The commit published is the one the checks tested**, `github.sha`, the merge of the pull request, which the job's default checkout builds; the comment names it. Building the head instead would publish a tree no check ran on whenever the base moved ahead.
- **The variables file is the `.env` of the Compose project** (`staging/.env`), passed with `--env-file` too, so that a command of Compose run on the server by hand reads it. Single quotes keep the `$` of the hash. Tried locally: a container of a trial project received the hash as written, and `docker compose config` of the staging file with a generated variables file passed, each drawn password in its connection.
- **The commands on the server.** Each step from the migration on uses `--no-deps`, so the publish, not `depends_on`, gives the order, and the migration runs once. Removing the volumes takes `rm --stop --force postgres garage` first, since a volume in use cannot be removed, then `docker volume rm --force` of `<project>_postgres-data` and `<project>_garage-data`, the project read from the `name:` of the Compose file. `stop`, `rm` and `volume rm --force` succeed with nothing to act on (tried on a project with no containers), so the first publish to a new server runs the same steps. `run` takes `-T`, since SSH gives it no terminal.
- **`/up` is asked from the runner**, through the public host name, not on the server: that proves the address, the firewall, the certificate, Caddy and the API at once, needs no tool on the server, and the 5 minutes cover the first certificates of a new server. The wait is in the same journal as the remote steps, so the order test covers it.
- **What the commands on the server print reaches the log of the job**, so that a failed publish can be read there: none of them carries a value, none prints the file or a configuration, and `pull` runs with `--quiet`.
- **A failed step stops the publish** and names the step; the next publish starts from the beginning, since each step recreates what it needs. A failed comment fails the job after staging shows the pull request.
- **The deploy key from `gh`**, without its last line break, is read as it is: Go's PEM reader does without it. A test gives it so.
- **Concurrency.** The workflow's `cancel-in-progress` is false for a pull request with the label, so that a push never cuts a publish short: its runs wait in turn. One gap is left: removing the label by hand and pushing while that pull request is publishing starts a run without the label, which cancels the publish; the next publish puts staging right.
- **The job builds the images itself**, with the Task targets the checks use, rather than taking them from the jobs of the checks: no new action is pinned, and no job of the checks pushes or uploads anything.
- **Where ticket 06 goes** is in its file, under From ticket 05.
- **After the code review** (2026-11-20): step 6 removes Mailpit too, whose e-mails live in its container, so no login code of an earlier pull request is left (story 29). A test reads each service of `deploy/compose.staging.yaml` that runs the binary or the seed, with what it extends, works out the environment its container receives from the variables file, and loads `config.Load` for each command it runs, its health check's included: a variable the binary requires that its service does not list fails the checks, not a publish (story 30). `derived` takes a value that cannot fail; the hash of the password of Mailpit is a value of its own.
